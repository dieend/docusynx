# docusynx

`docusynx` publishes deterministic Docusaurus content to managed wiki page
trees. The first target is Confluence Cloud.

The project has two parts:

- `docusaurus-plugin-docusynx` exports a versioned, target-neutral document
  bundle during the Docusaurus build.
- The `docusynx` Go CLI validates the bundle, discovers managed remote pages,
  creates a plan, and applies the plan through a target interface.

The Docusaurus source remains authoritative. Managed Confluence pages receive
an `autogenerated` label, a `docusynx-managed` label, and a visible link to the
source document.

## Initial release boundary

- Docusaurus 3.10
- All routes from the Docusaurus documentation and pages plugins
- Authored and generated documents
- Confluence Cloud REST API v2, with narrow REST API v1 calls for attachment
  upload and label writes
- Multiple named targets and publications
- Offline validation on merge requests
- Plan and apply on the default branch
- Deterministic component handlers for custom MDX components
- Fake-server tests and an opt-in live Confluence acceptance test

Terraform and external target processes are not part of the initial release.
The Go target interface is public so that another target can be added without
changing the synchronization engine.

## Development status

The Go module is `github.com/dieend/docusynx`. The Docusaurus integration is
published as the `docusaurus-plugin-docusynx` npm package.

## Installation

Install the CLI with Go:

```shell
go install github.com/dieend/docusynx/cmd/docusynx@latest
```

Install the Docusaurus plugin with your JavaScript package manager:

```shell
pnpm add docusaurus-plugin-docusynx
```

## Build and test

```shell
go test ./...
go vet ./...
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
```

The compiled Docusaurus plugin in
`packages/docusaurus-plugin-docusynx/dist` is committed. Run `pnpm build` after
a plugin source change and commit the updated output.

The live Confluence acceptance test skips unless all
`DOCUSYNX_TEST_CONFLUENCE_*` variables described in
`targets/confluence/live_acceptance_test.go` are set.

## Initial limitations

- A document move keeps its Confluence page history only when the document has
  an explicit `docusynx_id`. The fallback ID is derived from the Docusaurus
  document ID, so a move that changes that ID becomes a delete and create.
- The bundle records sidebar sibling order. The initial Confluence target keeps
  the page hierarchy but does not reorder existing Confluence siblings.
- Live Confluence acceptance requires a test space and credentials.

## CLI

```shell
docusynx validate --bundle build/docusynx/manifest.json
docusynx plan --config docusynx.yaml --publication product-docs --out plan.json
docusynx apply --config docusynx.yaml --plan plan.json
docusynx sync --config docusynx.yaml --publication product-docs
```

The configuration contains named targets and publications. Credentials and
remote IDs come from environment variables, not from the configuration file.
See [the example configuration](examples/docusynx.yaml).

See [the architecture](docs/architecture.md) for the system contracts and
safety rules. The [Confluence API notes](docs/confluence-api.md) record the
narrow REST API v1 compatibility calls.
