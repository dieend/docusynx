# Architecture

## Data flow

1. Docusaurus builds the complete site, including generated documents.
2. The export plugin converts each route to a target-neutral document.
3. The export plugin writes one canonical document bundle.
4. The CLI discovers pages that have matching management metadata.
5. The planner compares desired documents with the remote snapshot.
6. The apply operation creates page skeletons, resolves links, updates pages,
   and deletes removed managed pages.

The same document bundle and remote snapshot must always produce the same
ordered plan.

## Identity

Each document has a stable source ID. An explicit `docusynx_id` value has
priority. A Docusaurus route ID is the fallback. A title is never an identity.

Each publication-target pair has a separate namespace. A remote page belongs
to the publication only when its content property contains the same namespace
and source ID.

## Document bundle

The bundle is versioned independently from the CLI. A document contains:

- source ID and route;
- title, parent source ID, and deterministic order;
- target-neutral content blocks;
- source path, source URL, and source commit;
- content-addressed assets; and
- a canonical content hash.

Timestamps and machine-specific paths are not part of a content hash.

## Component handlers

A component handler is a deterministic TypeScript module. Registration uses
the MDX import source and export name. A handler receives literal component
properties and a restricted site-file reader. It returns target-neutral blocks
and assets. An unknown component is a validation error.

A handler must not call a wiki API, read credentials, use the network, or add a
timestamp to output.

## Target interface

The Go target interface provides managed page discovery, skeleton creation,
asset upload and reconciliation, page update, and page deletion operations.
The synchronization engine validates the bundle before it calls a target. The
first target is built into the CLI and supports Confluence Cloud.

An external process protocol is deferred until the target interface is stable.

## Confluence ownership

Every managed page has:

- an `autogenerated` label;
- a `docusynx-managed` label;
- a visible source notice; and
- a versioned content property with the namespace, source ID, desired hash,
  source path, source URL, and source commit.

The apply operation can update or delete only a page with matching ownership
metadata. It deletes child pages before their managed parent. It fails when an
unmanaged child prevents safe deletion.

## Automation policy

Change validation builds and validates the document bundle without remote
credentials. A deployment workflow can create a remote plan and apply it after
the change reaches its protected branch. The deployment system must serialize
apply operations for each publication and target.

Secrets come only from protected environment variables. Configuration, plans,
logs, document bundles, and state metadata must not contain credentials.

## Acceptance

Automated tests use a strict fake Confluence HTTP server. A separate opt-in
acceptance test creates a unique subtree in a live test space, verifies create,
update, idempotency, and deletion, and removes the subtree.
